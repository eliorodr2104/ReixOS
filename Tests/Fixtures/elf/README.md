# ELF corpus

Deliberately empty of binaries. The ELF images the host suites parse are built
in the test process by `makeELFImage` in
`Tests/Support/ELFLoaderFixtures.swift`, and this file records that as a
decision rather than an omission.

## Why generated and not checked in

* The interesting axes of an ELF fixture are `p_flags`, `p_vaddr`, `p_offset`
  alignment, `p_filesz` against `p_memsz`, and what the bytes between the end of
  a segment and the end of its last page hold. `ELFFixtureLayout` names each of
  them as a field, so a suite can break exactly one and leave the rest well
  formed. A checked-in binary fixes all of them at once, and a second axis needs
  a second binary.
* The builder is the only place the layout is written down, so a fixture cannot
  drift out of step with what the suites claim it is. A binary's provenance is a
  command in a README that nobody re-runs.
* `ElfParser` reads its structures by offset out of a buffer, so real bytes from
  a real linker buy nothing over generated bytes here: what varies between
  toolchains is which layouts they emit, and the point of the builder is to emit
  layouts on purpose, including ones no linker would.

## Where the real linker output is covered instead

The QEMU scenario matrix (`make vm-test`, `scripts/scenarios.sh`) boots the
image the project's own link step produced, so the loader does meet genuine
`ld` output on every run of the full `make test`, one level up, against the
real archive, rather than in a host unit test.

## If a binary is ever needed here

Keep it under a few KiB, record the exact `swiftc`/`ld.lld` invocation and both
versions the way `../dtb/README.md` does, and say in this file which layout axis
it pins that the builder cannot reach.
